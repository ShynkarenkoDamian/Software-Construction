## 1. Загальна картина

У лабі назву шаблону в умові не вказано — його треба **розпізнати за описом проблеми**. Усі три ситуації мають спільну ознаку: поведінка залежить від чогось (алгоритму, стану, типу), і це було написано через великий `if/switch` або копіюванням коду.

| Ознака в описі | Шаблон | Завдання варіанта 8 |
|---|---|---|
| Кілька **взаємозамінних алгоритмів** одного завдання, вибір (і зміна) під час виконання, розрахунок — один метод із розгалуженням за назвою схеми | **Strategy** | 1. Розрахунок вартості поїздки |
| **Однакова послідовність кроків**, окремі кроки різні, код скопійовано в кілька класів | **Template Method** | 2. Огляд авто |
| Поведінка залежить від **стану** об'єкта, усі методи містять однакове розгалуження за статусом, переходи між станами | **State** | 3. Стан авто |

### Принципи, на яких тримаються всі три шаблони

- **Open/Closed Principle (OCP)** — клас відкритий для розширення, закритий для змін: новий тариф / тип авто / стан додається новим класом, а не правкою існуючих.
- **Single Responsibility (SRP)** — кожен клас відповідає за одне: один тариф, один етап, один стан.
- **Dependency Inversion (DIP)** — контекст залежить від **абстракції** (`Tariff`, `CarInspection`, інтерфейс стану), а не від конкретних класів.
- **Інкапсуляція того, що змінюється** — змінну частину (формулу, крок, стан) виносимо з контексту.
- **Композиція замість наслідування** (Strategy, State) та **наслідування для повторного використання скелета** (Template Method).

Спільний «запах коду», який усуває кожен із шаблонів: **довгий `if/else if` або `switch`** за типом/станом/назвою схеми, повторений у кількох методах.

## 2. Strategy

### 2.1 Проблема
Є кілька способів виконати одну задачу (рахувати вартість поїздки): поминутний, кілометровий, комбінований, фіксований корпоративний, пізніше нічний. Усе було в одному методі:

```java
double calculate(Trip trip, String tariffName) {
    if (tariffName.equals("perMinute"))  { ... }
    else if (tariffName.equals("perKm")) { ... }
    else if (...)                        { ... }   // нічний тариф «зламав» кілометровий
}
```
Наслідки: додавання тарифу = правка метода, де легко зламати чужу гілку; змінити тариф клієнта без зміни коду неможливо; метод розростається й важко тестується.

### 2.2 Ідея
Кожен алгоритм виносимо в **окремий клас** за спільним інтерфейсом. Об'єкт-контекст зберігає посилання на інтерфейс і **делегує** розрахунок. Стратегію можна підміняти під час виконання.

### 2.3 Учасники

| Роль | Призначення | У проєкті |
|---|---|---|
| **Strategy** | Спільний інтерфейс алгоритму | `Tariff` |
| **ConcreteStrategy** | Конкретний алгоритм | `PerMinuteTariff`, `PerKmTariff`, `CombinedTariff`, `CorporateFixedTariff`, `NightTariff` |
| **Context** | Використовує стратегію, не знає деталей | `Trip` (через `Client`, який тримає обраний тариф) |
| **Client (у термінології GoF)** | Створює стратегію й передає контексту | `ScenarioRunner` |

> Увага: у GoF «Client» — це той, хто обирає стратегію. У домені є ще клас `Client` — клієнт каршерінгу, він просто зберігає обраний тариф.

### 2.4 Узагальнений приклад (поза доменом)

```java
interface PaymentStrategy { void pay(int amount); }
class CardPayment implements PaymentStrategy { public void pay(int a) { /* ... */ } }
class CashPayment implements PaymentStrategy { public void pay(int a) { /* ... */ } }

class Cart {
    private PaymentStrategy strategy;
    void setStrategy(PaymentStrategy s) { this.strategy = s; }
    void checkout(int sum) { strategy.pay(sum); }   // делегування
}
```

### 2.5 Коли застосовувати
- Багато варіантів одного алгоритму й великий `if/switch` між ними.
- Алгоритм треба **змінювати під час виконання**.
- Потрібно ізолювати логіку алгоритму від коду, що його використовує.

### 2.6 Переваги та недоліки
- ➕ OCP: новий алгоритм — новий клас; ➕ алгоритми взаємозамінні й тестуються окремо; ➕ усуває умовні оператори.
- ➖ більше класів; ➖ клієнт має знати про існування стратегій, щоб вибрати; ➖ для 2–3 простих варіантів може бути надмірним.

### 2.7 Що і як зроблено в проєкті

**Структура** (`task1_strategy/`):

```
Tariff (interface)            name(), calculate(Trip)
├── PerMinuteTariff           хвилини × ставка
├── PerKmTariff               кілометри × ставка
├── CombinedTariff            хвилини × ставка + кілометри × ставка
├── CorporateFixedTariff      фіксована сума
└── NightTariff               додано в сценарії 3 одним класом
Client                        тримає обраний Tariff, setTariff()
Trip (Context)                minutes, km, peakCoefficient; calculateCost()
```

**Ключовий код** — `Trip` не знає жодної формули:

```java
public double calculateCost() {
    Tariff tariff = client.getTariff();
    double base = tariff.calculate(this);       // делегування стратегії
    double total = base * peakCoefficient;      // години пік — не залежить від тарифу
    Log.log("Trip", ...);
    return total;
}
```

**Вимоги умови → як виконано**

| Вимога | Рішення |
|---|---|
| Кожен тариф окремо й взаємозамінний | Окремий клас на тариф, спільний інтерфейс `Tariff` |
| Тариф можна обрати й змінити під час виконання | `Client.setTariff(...)`, зміна логується |
| Новий тариф без змін у коді поїздки | `NightTariff` — один новий клас, `Trip`/`Client` не змінювались |

**Демонстраційний сценарій (з умови) у `ScenarioRunner.situation1Tariffs()`**

1. Поїздка 40 хв / 18 км за трьома тарифами — 160.00 / 162.00 / 170.00 грн.
2. Зміна тарифу клієнта на корпоративний — 150.00 грн.
3. Додано нічний тариф одним класом — 154.00 грн.

Приклад журналу (формат `[час] [джерело] подія`):

```
[09:00:02] [Trip] Іван Коваль, 40 хв / 18.0 км, тариф «Поминутний»: базова сума 160.00 грн, коефіцієнт години пік x1.0 -> до сплати 160.00 грн
[09:00:03] [Client] Іван Коваль: тариф змінено «Поминутний» → «Кілометровий»
[09:00:04] [Trip] Іван Коваль, 40 хв / 18.0 км, тариф «Кілометровий»: базова сума 162.00 грн, ...
```
З журналу видно, **який алгоритм** працює в кожен момент (вимога умови: «видно, який алгоритм виконується»).

**Години пік.** В описі згадано підвищувальний коефіцієнт. Він реалізований у `Trip` як множник суми будь-якого тарифу (не залежить від типу тарифу). Додатковий рядок демонстрації: поминутний тариф з коефіцієнтом 1.5 → 240.00 грн.

**Припущення.** Ставки (4.00 грн/хв, 9.00 грн/км, комбінований 2.00 + 5.00, корпоративний 150.00, нічний 2.50 + 3.00) умовні — в умові їх немає. Змінюються в `ScenarioRunner`.

**Діаграма:** `docs/diagrams/task1_strategy/task1-strategy.*` (Mermaid; `.mmd`, `.svg`, `.png`, `.pdf`).

### 2.8 Питання до захисту
- *Чому Strategy, а не State?* Тариф обирає клієнт (ззовні), стратегії **не знають одна про одну** й не перемикаються самі; стани ж самі керують переходами.
- *Чому не `switch` за назвою тарифу?* Порушує OCP: кожен новий тариф — правка метода, ризик зламати інші (саме так «зламався» кілометровий).
- *Де зберігається коефіцієнт пік і чому не в тарифі?* У `Trip`: він однаковий для всіх тарифів, дублювати його в кожному класі — повторення.
- *Як додати новий тариф?* Новий клас, що реалізує `Tariff` (приклад — `NightTariff`).
- *Як змінити тариф клієнта на льоту?* `client.setTariff(new CorporateFixedTariff(150))`.

## 3. Template Method

### 3.1 Проблема
Огляд авто перед поверненням у парк проходить **однакові етапи**: зовнішній огляд → салон → енергія → технічна перевірка → повернення в доступні. Для бензинового, гібрида й електромобіля код етапів був **скопійований у три класи**; коли змінилась вимога до зовнішнього огляду, виправили лише бензинові — решта розійшлись.

### 3.2 Ідея
Базовий клас у **одному методі-шаблоні** задає незмінний скелет алгоритму. Кроки, що різняться, — абстрактні методи (обов'язково реалізувати) або **hook-и** (мають реалізацію за замовчуванням, можна перевизначити). Підкласи **не можуть змінити порядок**.

### 3.3 Учасники

| Роль | Призначення | У проєкті |
|---|---|---|
| **AbstractClass** | Містить метод-шаблон, спільні кроки, абстрактні кроки й hook-и | `CarInspection` |
| **Template method** | `final`-метод із порядком кроків | `CarInspection.inspect()` |
| **ConcreteClass** | Реалізує кроки, що відрізняються | `PetrolCarInspection`, `HybridCarInspection`, `ElectricCarInspection`, `GasCarInspection` |
| **Hook** | Необов'язковий крок із поведінкою за замовчуванням | `wash()`, `sendForEnergy()` |

### 3.4 Узагальнений приклад (поза доменом)

```java
abstract class DataExporter {
    public final void export() {          // шаблонний метод — final
        open();
        String data = read();             // абстрактний крок
        data = format(data);              // hook із поведінкою за замовчуванням
        write(data);                      // абстрактний крок
        close();
    }
    protected abstract String read();
    protected abstract void write(String d);
    protected String format(String d) { return d; }
    private void open()  { /* спільне */ }
    private void close() { /* спільне */ }
}
```

### 3.5 Принцип Голлівуду
«Не телефонуйте нам — ми самі вам зателефонуємо». Базовий клас **сам викликає** методи підкласів у потрібний момент, а не навпаки. Це інверсія керування: скелетом володіє батьківський клас.

### 3.6 Коли застосовувати
- Кілька класів мають **однаковий алгоритм** з різними окремими кроками.
- Треба **гарантувати порядок** кроків і запобігти дублюванню.
- Потрібні точки розширення (hook-и), але не повна заміна алгоритму.

### 3.7 Переваги та недоліки
- ➕ немає дублювання, зміна спільного кроку — в одному місці; ➕ підкласи не можуть порушити порядок; ➕ легко додати новий тип.
- ➖ працює через **наслідування** (жорстка зв'язка з базовим класом); ➖ багато підкласів при великій кількості варіацій; ➖ можна порушити принцип підстановки Лісков, якщо підклас «ламає» очікування базового.

### 3.8 Що і як зроблено в проєкті

**Метод-шаблон** (`task2_template_method/CarInspection.java`):

```java
public final void inspect(Car car) {
    exteriorInspection(car);            // 1. спільний (private)
    interiorCheck(car);                 // 2. спільний (private)
    wash(car);                          //    hook: за замовчуванням «мийка не потрібна»
    boolean energyOk = checkEnergy(car);//  3. абстрактний
    technicalCheck(car);                //  4. абстрактний
    if (energyOk) returnToAvailable(car);   // 5. спільний
    else          sendForEnergy(car);       // 5'. hook: на поповнення енергії
}
```

**Типи кроків**

| Крок | Вид | Хто визначає |
|---|---|---|
| Зовнішній огляд, перевірка салону, повернення в доступні | спільні, `private` | тільки `CarInspection` — підкласи змінити не можуть |
| Перевірка рівня енергії, технічна перевірка | `abstract` | кожен тип авто |
| Мийка | hook | за замовчуванням «не потрібна»; `PetrolCarInspection` перевизначає |
| Дія при малій енергії | hook | за замовчуванням — «на поповнення енергії»; `ElectricCarInspection` — «на зарядку» |

**Вимоги умови → як виконано**

| Вимога | Рішення |
|---|---|
| Послідовність етапів в одному місці, змінити окремим типам не можна | `final inspect()`; спільні етапи — `private` |
| Кожен тип визначає лише те, що відрізняється | Тільки `checkEnergy`, `technicalCheck` (+ за потреби hook-и) |
| Необов'язкові етапи (мийка) мають поведінку за замовчуванням | `wash()` — hook; Petrol перевизначає, Electric/Gas — ні |
| Новий тип одним класом | `GasCarInspection` додано без змін в інших класах |

**Енергія < порогу.** Після технічної перевірки авто **не повертається** в доступні, а іде на поповнення енергії (для електромобіля — на зарядку). Це реалізує сценарій «заряд 15% → на зарядку замість повернення».

**Демонстраційний сценарій (з умови) у `ScenarioRunner.situation2Inspection()`**

1. Бензинове авто — усі етапи, мийка виконана, повернуто в доступні.
2. Електромобіль із зарядом 15% тією самою процедурою — відправлено на зарядку.
3. Додано тип «авто на газу» одним класом.

Приклад журналу:

```
[09:00:26] [ElectricCarInspection] Початок огляду: CE5678BB (енергія 15%, статус: повернено з поїздки)
[09:00:29] [ElectricCarInspection] (необов'язковий етап) Мийка не потрібна — пропущено
[09:00:30] [ElectricCarInspection] Етап 3. Рівень заряду 15% (мінімум 20%) — недостатньо
[09:00:32] [ElectricCarInspection] Етап 5. Заряд низький — авто відправлено на зарядку замість повернення в доступні
[09:00:33] [ElectricCarInspection] Огляд завершено: CE5678BB (енергія 15%, статус: відправлено на поповнення енергії)
```
З журналу видно, **який крок процесу** виконується (вимога умови).

**Припущення.** Мінімальні рівні енергії (15% для бензину/гібрида/газу, 20% для електромобіля) і перелік робіт технічної перевірки — умовні. Мийка викликається між етапами 2 і 3.

**Діаграма:** `docs/diagrams/task2_template_method/task2-template-method.*`.

### 3.9 Питання до захисту
- *Чому Template Method, а не Strategy?* Порядок етапів **спільний і незмінний**, а різняться лише окремі кроки, що визначаються **типом авто** (не змінюється під час життя об'єкта). Strategy підміняє весь алгоритм і дає змінювати його на льоту.
- *Навіщо `final` на `inspect()`?* Щоб підклас не міг змінити порядок етапів — саме так розійшлись три копії коду.
- *Різниця hook / abstract?* Abstract — обов'язково реалізувати, hook — є поведінка за замовчуванням, перевизначення необов'язкове.
- *Чому спільні етапи `private`?* Підклас не повинен їх перевизначати: зміна вимог до зовнішнього огляду робиться в одному місці.
- *Як додати новий тип?* Успадкувати `CarInspection`, реалізувати два абстрактні методи (приклад — `GasCarInspection`).

## 4. State

> **Реалізує колега** (пакет `task3_state`). Нижче — теорія, яку мають знати обидва учасники команди.

### 4.1 Проблема
Авто проходить стани: доступне → заброньоване → в поїздці → на паузі → на обслуговуванні. Від стану залежить, що дозволено (забронювати можна лише доступне, завершити поїздку — лише в поїздці). Кожен метод авто містив однакове розгалуження за статусом, а додавання стану «евакуація» вимагало змін у всіх методах.

### 4.2 Ідея
Кожен стан — **окремий клас**, що реалізує спільний інтерфейс усіх операцій. Контекст (авто) делегує виклики **поточному об'єкту-стану**. Стани **самі** виконують перехід, замінюючи стан у контексті. Недопустима операція — зрозуміла відмова в цьому стані.

### 4.3 Учасники

| Роль | Призначення |
|---|---|
| **Context** | Авто: тримає поточний стан, делегує йому операції, має `setState()` |
| **State** | Інтерфейс (або абстрактний клас) з методами всіх операцій |
| **ConcreteState** | Поведінка в конкретному стані + переходи в інші |

### 4.4 Узагальнений приклад

```java
interface State { void reserve(Car c); void start(Car c); }
class Available implements State {
    public void reserve(Car c) { c.setState(new Reserved()); }
    public void start(Car c)   { System.out.println("Спершу забронюйте"); }
}
class Car {
    private State state = new Available();
    void setState(State s) { state = s; }
    void reserve() { state.reserve(this); }   // без if/switch
}
```

### 4.5 Переваги та недоліки
- ➕ немає розгалужень за статусом; ➕ новий стан не змінює контекст; ➕ переходи описані в самих станах.
- ➖ багато класів; ➖ стани знають про сусідні стани (зв'язність між ними).

### 4.6 Що має бути в Завданні 3 (за умовою варіанта 8)
- Поведінка при кожній операції визначається поточним станом **без розгалужень**.
- Переходи описані **самими станами**, недопустима операція повертає зрозуміле повідомлення.
- Новий стан («евакуація») не потребує змін у класі авто.
- Сценарій: доступне → заброньоване → в поїздці → на паузі → в поїздці → доступне; бронювання не підтверджене за 20 хв → знову доступне; спроба бронювання авто на обслуговуванні → відмова.

## 5. Порівняння шаблонів

| | Strategy | State | Template Method |
|---|---|---|---|
| Що змінюється | Весь алгоритм | Поведінка залежно від стану | Окремі кроки алгоритму |
| Механізм | Композиція (делегування) | Композиція (делегування) | Наслідування |
| Хто обирає варіант | Клієнт ззовні | Сам контекст/стани (переходи) | Тип підкласу (фіксується при створенні) |
| Змінюється під час виконання | Так, `setTariff` | Так, самі стани | Ні |
| Знають одне про одного | Ні, стратегії незалежні | Так, стани знають сусідів | Підклас залежить від базового |
| Приклад у лабі | Тарифи | Стани авто | Огляд авто |

**Strategy vs State** мають однакову структуру (контекст + інтерфейс + реалізації), різниця в **наміру**: стратегію вибирають, стан змінюється сам унаслідок подій.
**Template Method vs Strategy**: перший змінює *частини* алгоритму наслідуванням, другий замінює *весь* алгоритм композицією.

## 6. Підготовка до захисту

Умова лаби: обидва члени команди володіють **усією** кодовою базою й можуть захистити будь-який шаблон.

**Як відповідати на «поясніть рішення ситуації»** (схема з 5 пунктів):
1. Яка була проблема (який `if/switch` або дублювання).
2. Який шаблон і **за якою ознакою** його розпізнано.
3. Які класи відповідають ролям шаблону (див. діаграму).
4. Як змінюється код при додаванні нового варіанта (один новий клас).
5. Що видно в журналі демонстрації.

**Швидка шпаргалка**
- Strategy = «вибираю алгоритм»; State = «поведінка залежить від стану»; Template Method = «скелет один, кроки різні».
- Нічний тариф → `NightTariff`; тип «авто на газу» → `GasCarInspection`; стан «евакуація» → новий клас стану.
- Крос-рев'ю (Завдання 5): діаграма відповідає коду? рішення справді усуває проблему? раннер відтворює сценарій?
