## 1. Загальна картина

Назву шаблону в умові не вказано — його треба **розпізнати за описом**.

| Ознака в описі | Шаблон | Завдання варіанта 8 |
|---|---|---|
| Структура типів об'єктів **стабільна**, а **нові операції** з'являються постійно; кожну операцію додавали методом у всі класи | **Visitor** | 1. Операції над парком (страхування, ТО, CO2) |
| Треба **зберегти й відновити стан** об'єкта, а його поля закриті й відкривати їх заборонено | **Memento** | 2. Налаштування авто для клієнта |
| Різним службам потрібен **різний порядок обходу** колекції без знання її внутрішньої структури | **Iterator** | 3. Обхід авто для обслуговування |

### Принципи
- **Open/Closed** — нова операція (Visitor) — новий клас, класи авто не змінюються.
- **Single Responsibility** — класи авто зберігають дані, а страхування/ТО/викиди живуть у окремих візиторах; профіль клієнта лише *зберігає* знімки; обхід — окремий об'єкт-ітератор.
- **Інкапсуляція** — Memento зберігає й відновлює стан, **не відкриваючи** поля; Iterator приховує внутрішню структуру колекції.
- **Подвійна диспетчеризація** (Visitor) — вибір дії залежить від двох типів: візитора й елемента.

## 2. Visitor

### 2.1 Проблема
Парк складається з авто різних типів (бензинові, гібриди, електромобілі, мікроавтобуси). Структура типів майже не змінюється, а **нові операції** з'являються регулярно: розрахунок страхування, планування ТО, викиди CO2. Кожну операцію додавали **методом у всі класи авто**, і класи перетворились на звалище не пов'язаної логіки:

```java
class PetrolCar   { double insurance() {...}  void planService() {...}  double co2() {...} }
class ElectricCar { double insurance() {...}  void planService() {...}  double co2() {...} }
// ... нова операція = правка кожного класу
```

### 2.2 Ідея
Операції виносяться в окремі класи-**візитори**. Кожен елемент має єдиний метод `accept(visitor)`, який викликає `visitor.visit(this)` — відповідний **саме його типу**. Нова операція = новий візитор, класи елементів не змінюються.

### 2.3 Учасники

| Роль | Призначення | У проєкті |
|---|---|---|
| **Visitor** | Інтерфейс із методом `visit` для кожного типу елемента | `FleetVisitor` |
| **ConcreteVisitor** | Конкретна операція | `InsuranceVisitor`, `MaintenanceVisitor`, `Co2EmissionsVisitor` |
| **Element** | Інтерфейс/клас з `accept(visitor)` | `Vehicle` |
| **ConcreteElement** | Конкретний тип, реалізує `accept` | `PetrolCar`, `HybridCar`, `ElectricCar`, `Minibus` |
| **ObjectStructure** | Колекція елементів, проходить по всіх | `Fleet` |

### 2.4 Подвійна диспетчеризація

Java вибирає перевантаження за **статичним** типом аргумента, тому `visitor.visit(vehicle)` для `Vehicle` не знав би конкретного типу. Рішення — двокроковий виклик:

```
fleet.accept(visitor)
   └── для кожного авто: vehicle.accept(visitor)      // 1-й вибір: за динамічним типом авто (поліморфізм)
          └── visitor.visit(this)                      // 2-й вибір: перевантаження visit(PetrolCar|HybridCar|...)
```

Усередині `PetrolCar.accept` `this` має тип `PetrolCar`, тому викликається саме `visit(PetrolCar)`.

### 2.5 Узагальнений приклад (поза доменом)

```java
interface ShapeVisitor { void visit(Circle c); void visit(Square s); }
interface Shape { void accept(ShapeVisitor v); }
class Circle implements Shape { public void accept(ShapeVisitor v) { v.visit(this); } }
class Square implements Shape { public void accept(ShapeVisitor v) { v.visit(this); } }

class AreaVisitor implements ShapeVisitor {
    double total;
    public void visit(Circle c) { total += Math.PI * c.r * c.r; }
    public void visit(Square s) { total += s.a * s.a; }
}
```

### 2.6 Коли застосовувати
- Структура **типів** елементів стабільна, а набір **операцій** росте.
- Операції не мають «засмічувати» класи елементів.
- Потрібно виконати операцію над усією структурою за один прохід.

### 2.7 Переваги та недоліки
- ➕ OCP для операцій: нова операція — один клас; ➕ споріднена логіка зібрана в одному місці; ➕ візитор може накопичувати стан (суму, лічильник).
- ➖ **додавання нового типу елемента ламає всі візитори** (треба додати `visit` у кожен) — головний недолік; ➖ елементи мають відкривати дані (геттери), що послаблює інкапсуляцію; ➖ складніше за прості методи.

### 2.8 Що і як зроблено в проєкті

**Структура** (`task1_visitor/`):

```
Vehicle (Element, abstract)           дані: plate, value, mileageKm, monthlyKm; accept(FleetVisitor)
├── PetrolCar, HybridCar, ElectricCar
└── Minibus (+ seats)
FleetVisitor (Visitor)                visit(PetrolCar|HybridCar|ElectricCar|Minibus), onFinish()
├── InsuranceVisitor                  страхування
├── MaintenanceVisitor                планування ТО
└── Co2EmissionsVisitor               викиди CO2 — додано одним класом
Fleet (ObjectStructure)               add(), accept(visitor), logState()
```

**Ключовий код** — елемент не містить бізнес-логіки, лише «пропускає» візитора:

```java
// PetrolCar
@Override
public void accept(FleetVisitor visitor) { visitor.visit(this); }

// Fleet — один прохід по всьому парку
public void accept(FleetVisitor visitor) {
    for (Vehicle vehicle : vehicles) vehicle.accept(visitor);
    visitor.onFinish();            // підсумок операції
}
```

**Вимоги умови → як виконано**

| Вимога | Рішення |
|---|---|
| Нова операція без зміни класів авто | `Co2EmissionsVisitor` — один новий клас |
| Кожна операція окремо, логіка для кожного типу | Візитор має `visit` для кожного типу авто |
| Один прохід по всьому парку | `Fleet.accept(visitor)` |
| У журналі видно стан до й після | `Fleet.logState("до операції")` / `("після операції")`; авто операціями не змінюються |

**Демонстраційний сценарій (з умови) у `ScenarioRunner.situation1FleetOperations()`**

1. Страхування всього парку: 24000.00 / 33750.00 / 55000.00 / 87600.00 / 52500.00 — разом 252850.00 грн.
2. ТО для того самого парку: для кожного авто — інтервал, наступний пробіг ТО, залишок і перелік робіт.
3. Викиди CO2 (додано одним класом): разом 1167.0 кг за місяць.

Приклад журналу:

```
[09:00:07] [InsuranceVisitor] CE1001AA (бензинове): страхування 24000.00 грн — 4% від вартості
[09:00:10] [InsuranceVisitor] CE1004AA (мікроавтобус): страхування 87600.00 грн — 6% від вартості + 400 грн за кожне з 9 місць
[09:00:12] [InsuranceVisitor] Разом за парк: 252850.00 грн
[09:00:45] [Co2EmissionsVisitor] CE1001AA (бензинове): 150 г/км x 2100 км = 315.0 кг CO2
```

**Припущення.** У тексті лаби немає формул і значень, тому умовні: відсотки страхування (4% / 4.5% / 5% / 6% + 400 грн за місце для мікроавтобуса), інтервали ТО (10 000 / 15 000 / 20 000 / 8 000 км), викиди (150 / 90 / 0 / 230 г/км), а також вартість і пробіги авто в демонстрації. Для звіту CO2 у кожного авто є «пробіг за місяць» (`monthlyKm`). Змінюються константами у візиторах і в `ScenarioRunner`.

### 2.9 Питання до захисту
- *Чому Visitor?* Типи авто стабільні, нові операції з'являються постійно, і їх додавали в усі класи. Visitor виносить операції з класів авто.
- *Що таке подвійна диспетчеризація й де вона тут?* `fleet.accept → vehicle.accept → visitor.visit(this)`: перший виклик вибирає тип авто, другий — перевантаження `visit` за типом `this`.
- *Головний недолік?* Додати новий тип авто (наприклад, «квадроцикл») — значить додати `visit` у `FleetVisitor` і в усі візитори.
- *Чому не просто метод у класах авто?* Класи стануть звалищем несуміжної логіки (страхування, ТО, екологія).
- *Навіщо `onFinish()`?* Візитор накопичує підсумок (загальна сума, кількість), `Fleet` викликає його після обходу.
- *Як додати операцію?* Новий клас, що реалізує `FleetVisitor` (приклад — `Co2EmissionsVisitor`).

## 3. Memento

### 3.1 Проблема
Клієнт налаштовує авто: положення сидіння, дзеркала, клімат, мультимедіа. Налаштування мають зберігатись у профілі клієнта й відновлюватись у **будь-якому авто тієї ж моделі**; під час поїздки клієнт може повернутися до збережених налаштувань. Внутрішній стан систем авто **закритий**, відкривати поля заради збереження копії **заборонено**.

Наївне рішення (геттери для всіх полів + сеттери в профілі) руйнує інкапсуляцію: будь-який клас може читати й псувати внутрішній стан.

### 3.2 Ідея
Сам об'єкт (**Originator**) створює свій **знімок** (Memento) — «капсулу» зі станом, і сам же відновлюється з неї. Зовнішній об'єкт (**Caretaker**) лише **зберігає** знімки й повертає їх, але не бачить їхнього вмісту і не може його змінити.

### 3.3 Учасники

| Роль | Призначення | У проєкті |
|---|---|---|
| **Originator** | Створює знімок і відновлюється з нього | `Car` (`save()`, `restore()`) |
| **Memento** | Зберігає стан Originator | `Car.Snapshot` (вузький інтерфейс) і `Car.SettingsState` (повний знімок) |
| **Caretaker** | Зберігає знімки, не знає їхнього вмісту | `ClientProfile` |

### 3.4 Вузький і широкий інтерфейс
Memento має два «обличчя»:
- **вузький** — для Caretaker: майже нічого (у нас лише `getModel()`);
- **широкий** — для Originator: усі поля стану.

У Java це реалізується **приватним вкладеним класом**: `SettingsState` — `private static final class` усередині `Car`, його поля бачить лише `Car`. Назовні повертається значення типу інтерфейсу `Snapshot`.

### 3.5 Узагальнений приклад (поза доменом)

```java
class Editor {
    private String text;
    public Memento save() { return new State(text); }
    public void restore(Memento m) { this.text = ((State) m).text; }

    public interface Memento {}                       // вузький інтерфейс
    private static class State implements Memento {   // широкий — тільки для Editor
        private final String text;
        State(String t) { this.text = t; }
    }
}
class History {                                        // Caretaker
    private final Deque<Editor.Memento> stack = new ArrayDeque<>();
    void push(Editor.Memento m) { stack.push(m); }
    Editor.Memento pop() { return stack.pop(); }
}
```

### 3.6 Коли застосовувати
- Потрібен **undo/відкат/контрольні точки**.
- Прямий доступ до полів (геттери) порушив би інкапсуляцію.
- Знімок має бути **незмінним** і недоступним для зовнішнього коду.

### 3.7 Переваги та недоліки
- ➕ зберігає інкапсуляцію; ➕ спрощує Originator (історію веде Caretaker); ➕ знімок незмінний.
- ➖ багато знімків — витрати пам'яті; ➖ Caretaker має стежити за життєвим циклом знімків; ➖ у мовах без вкладених приватних класів складно гарантувати приватність.

### 3.8 Що і як зроблено в проєкті

**Структура** (`task2_memento/`):

```
Car (Originator)             поля: model, seatPosition, mirrorAngle, climateTemperature, volume, radioStation
├── interface Snapshot       getModel()                       — вузький інтерфейс знімка
└── private SettingsState    усі поля стану, приватні final    — повний знімок
ClientProfile (Caretaker)    Map<String, Snapshot>; save(name, car), restore(name, car)
```

**Ключовий код**

```java
public Snapshot save() {                                   // Originator створює знімок
    return new SettingsState(model, seatPosition, mirrorAngle,
                             climateTemperature, volume, radioStation);
}

public boolean restore(Snapshot snapshot) {                // Originator відновлюється
    SettingsState state = (SettingsState) snapshot;
    if (!state.model.equals(model)) { /* відмова */ return false; }
    this.seatPosition = state.seatPosition; ...            // поля знімка бачить лише Car
    return true;
}
```

`ClientProfile` зберігає `Snapshot` у `Map` за іменем («основні») і віддає авто — читати чи змінювати вміст він **не може**: у `Snapshot` немає ні методів читання полів, ні методів зміни, а поля `SettingsState` — `private final`.

**Вимоги умови → як виконано**

| Вимога | Рішення |
|---|---|
| Зберегти/відновити стан, не розкриваючи структуру | Приватний вкладений `SettingsState`, зовні — лише `Snapshot` |
| Збереженими станами керує окремий об'єкт профілю, який не може змінювати їхній вміст | `ClientProfile` бачить тільки вузький інтерфейс |
| Відновити в іншому авто тієї ж моделі | `restore()` приймає знімок від будь-якого авто тієї ж моделі, інша модель — відмова |
| Журнал: стан до й після | `Car.describe()` виводиться до й після відновлення |

**Демонстраційний сценарій (з умови) у `ScenarioRunner.situation2CarSettings()`**

1. Налаштувати авто CE1234AA й зберегти в профіль («основні»).
2. Змінити налаштування під час поїздки, потім відновити збережені.
3. Відновити налаштування в іншому авто тієї ж моделі (CE5678BB).
4. Додатково: спроба відновити в авто іншої моделі — відмова, стан авто не змінюється.

Приклад журналу:

```
[09:01:01] [CE1234AA] Стан до відновлення: Hyundai Ioniq: сидіння 7, дзеркала 12°, клімат 18.0 °C, мультимедіа: гучність 3, «Радіо Культура»
[09:01:02] [Profile:Іван Коваль] Налаштування «основні» відновлено в авто CE1234AA
[09:01:03] [CE1234AA] Стан після відновлення: Hyundai Ioniq: сидіння 5, дзеркала 12°, клімат 21.5 °C, мультимедіа: гучність 8, «Радіо Промінь»
[09:01:10] [CE9999CC] Відмова: збережені налаштування для моделі «Hyundai Ioniq», а це авто — «Kia Rio»
```

**Припущення.** Числові значення налаштувань умовні. У знімок входить назва моделі, щоб перевірити «ту саму модель» при відновленні. Профіль зберігає знімки за іменем (історії відкату не потрібно за умовою).

**Діаграма:** `docs/diagrams/task2_memento/task2-memento.*`.

### 3.9 Питання до захисту
- *Чому Memento, а не геттери й сеттери?* Вони відкрили б внутрішній стан усім; Memento дозволяє зберегти стан без відкриття полів.
- *Як гарантовано, що профіль не змінить знімок?* Поля `SettingsState` приватні й `final`, у `Snapshot` немає методів доступу до стану; саме `restore()` читає поля, бо це вкладений клас `Car`.
- *Хто що знає?* `Car` знає все про стан; `ClientProfile` — лише що існує знімок і для якої він моделі.
- *Memento vs Command (undo)?* Command зберігає *дію*, яку можна скасувати; Memento — *стан*, до якого можна повернутися.
- *Чому перевіряємо модель?* Знімок має сенс лише для авто тієї ж моделі (різні набори налаштувань).

## 4. Iterator

### 4.1 Проблема
Авто зберігаються за зонами міста, а в зонах — за майданчиками (з вкладеними зонами). Кожен модуль писав **власні вкладені цикли** по внутрішній структурі: службі обслуговування — авто з низьким зарядом у порядку маршруту, диспетчеру — усі авто зони, аналітиці — авто, що простоюють понад добу. Після додавання вкладених зон усі цикли зламались.

### 4.2 Ідея
Колекція повертає об'єкт-**ітератор** (`hasNext()`, `next()`), який обходить елементи, **не розкриваючи внутрішньої структури**. Різні способи обходу — різні класи-ітератори. Кожен ітератор має **власний стан**, тому кілька обходів однієї колекції можуть вестись одночасно й незалежно.

### 4.3 Учасники

| Роль | Призначення |
|---|---|
| **Iterator** | Інтерфейс обходу (`hasNext`, `next`) |
| **ConcreteIterator** | Конкретний порядок/фільтр обходу, тримає свою позицію |
| **Aggregate (Iterable)** | Інтерфейс колекції з методом створення ітератора |
| **ConcreteAggregate** | Колекція (зони, майданчики), повертає потрібний ітератор |

### 4.4 Узагальнений приклад

```java
interface Iterator<T> { boolean hasNext(); T next(); }

class ZoneIterator implements Iterator<Car> {
    private final List<Car> cars; private int pos = 0;       // власна позиція
    ZoneIterator(List<Car> cars) { this.cars = cars; }
    public boolean hasNext() { return pos < cars.size(); }
    public Car next() { return cars.get(pos++); }
}
```
У Java є стандартні `java.util.Iterator` та `Iterable` (цикл `for-each`).

### 4.5 Переваги та недоліки
- ➕ клієнт не залежить від структури колекції; ➕ різні способи обходу — різні класи (SRP); ➕ одночасні незалежні обходи; ➕ вкладені структури ховаються всередині ітератора.
- ➖ для простих списків надмірний; ➖ може бути менш ефективний за прямий доступ.

### 4.6 Що і як зроблено в проєкті

**Структура** (`task3_iterator/`):

```
Zone (ConcreteAggregate, Iterable<ParkedCar>)   зони з вкладеними зонами; iterator(), lowChargeRouteIterator(), idleIterator()
├── ParkingLot                                  майданчик: назва, routeOrder (номер зупинки маршруту), авто
│   └── ParkedCar                               plate, chargePercent, idleHours

└── FilteredCarIterator (abstract)              фільтр accepts()
    ├── LowChargeRouteIterator                  заряд < порогу, у порядку маршруту
    └── IdleCarIterator                         простій понад задану кількість годин
```

**Ключовий код**


**Вимоги умови → як виконано**

| Вимога | Рішення |
|---|---|
| Модулі обходять авто, не знаючи структури зон і майданчиків | Клієнти працюють лише з `Iterator<ParkedCar>`; структура прихована всередині `Zone` і ітераторів |
| Кілька способів обходу, кожен окремо | `ZoneCarIterator`, `LowChargeRouteIterator`, `IdleCarIterator` — окремі класи |
| Кілька обходів одночасно й незалежно | Кожен ітератор має власний стан; сценарій 3 чергує `next()` двох ітераторів і перевіряє, що результати збігаються з окремими обходами |

### 4.7 Питання до захисту
- *Чому Iterator?* Різні служби потребують різного порядку обходу, а власні вкладені цикли ламалися після зміни структури; Iterator ховає структуру й виносить обхід в окремі класи.
- *Чим це краще за вкладені цикли?* Додали вкладені зони — змінився лише код ітератора, клієнти не торкнулися.
- *Чому обходи незалежні?* Кожен ітератор тримає власний стан (позицію, стек); колекція стану обходу не зберігає.
- *Навіщо `FilteredCarIterator`?* Спільна логіка «пропустити непідхожі» в одному місці; нащадки задають лише `accepts()`.
- *Що буде, якщо змінити колекцію під час обходу?* Стандартні списки можуть кинути `ConcurrentModificationException` або дати застарілі дані; у лабі колекція під час обходів не змінюється.
- *Iterator vs Visitor?* Iterator — «в якому порядку обійти», Visitor — «що зробити з елементом залежно від його типу».

## 5. Порівняння шаблонів

| | Visitor | Memento | Iterator |
|---|---|---|---|
| Що вирішує | Нові операції над стабільною структурою типів | Збереження/відновлення стану без порушення інкапсуляції | Обхід колекції без знання її структури |
| Що виносить | Операції з класів елементів | Стан у капсулу-знімок | Логіку обходу з колекції |
| Додати нове — просто | Нова операція | — | Новий спосіб обходу |
| Додати нове — складно | Новий тип елемента | — | — |
| У лабі | Страхування / ТО / CO2 | Налаштування авто | Обхід авто по зонах |

**Visitor vs Iterator**: Iterator відповідає на питання «*у якому порядку* обійти елементи», Visitor — «*що зробити* з кожним елементом залежно від його типу». Їх часто поєднують: ітератор обходить, візитор виконує операцію.
**Memento vs просте копіювання**: копія полів вимагає їх відкрити, Memento — ні.
**Memento vs Command**: Command зберігає дію для скасування, Memento — стан.
