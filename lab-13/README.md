## 3.1. Як влаштовано Завдання 2 (в термінах домену)

| Роль у шаблоні | Клас | Що робить |
|---|---|---|
| Handler | `AccessCheck` (абстрактний) | знає наступну ланку (`next`); метод `handle()` пише в журнал, викликає `verify()` і або зупиняє клієнта, або передає запит далі |
| ConcreteHandler | `DriverLicenseCheck`, `DrivingExperienceCheck`, `DebtCheck`, `FundsCheck`, `BanCheck` | одна перевірка: лише метод `verify()` — повертає `null` (пройшов) або причину відмови |
| Запит | `TripRequest` (+ `Customer`, `CarClass`) | клієнт, авто, клас авто, потрібна сума на картці; саме він рухається по ланцюгу |
| Збирач ланцюга / точка входу | `TripAccessService` | `configure(класАвто, перевірки...)` збирає ланцюг із заданих перевірок у заданому порядку; `requestAccess()` віддає запит першій ланці |
| Client | `Main` | під час виконання налаштовує ланцюги й подає запити |
| Результат | `AccessResult` | допущено чи ні, яка ланка зупинила (або остання), причина |

### Відповідність вимогам лаби (Завдання 2)
| Вимога з тексту лаби | Як виконано |
|---|---|
| Кожна перевірка окремо: або зупиняє клієнта з причиною, або передає далі | 5 класів-нащадків `AccessCheck`; `verify()` повертає причину → `handle()` зупиняє, інакше викликає `next.handle()` |
| Склад і порядок налаштовуються під час виконання, окремо для звичайних і преміальних авто | `TripAccessService.configure(CarClass.STANDARD, ...)` і `configure(CarClass.PREMIUM, ...)` у `Main.scenarioTripAccess()`; стаж водіння є лише в преміальному ланцюгу |
| Нова перевірка не потребує змін в існуючих | новий клас-нащадок `AccessCheck` (наприклад `AgeCheck` для спорткарів) + додати його в виклик `configure()`; жодна існуюча перевірка не змінюється |
| Сценарій: клієнт проходить усі перевірки для звичайного авто | Олена Коваль: 4 ланки пройдено, «ДОПУСК НАДАНО» |
| Сценарій: клієнт із заборгованістю зупиняється, наступні не виконуються | Петро Мельник: зупинений на `DebtCheck`, `FundsCheck` і `BanCheck` у журналі відсутні |
| Сценарій: стаж 1 рік, преміальне авто — відмова на перевірці стажу | Андрій Бойко: відмова на `DrivingExperienceCheck` (1 р. < 3 р.) |
| У журналі видно, хто отримав запит і хто обробив | `[TripAccessService]` отримав → кожна ланка пише «отримав запит» → ланка, що зупинила, пише «ЗУПИНЯЄ клієнта: причина» |

## 4. Теорія для захисту

### Command (команда) — наш шаблон
- **Ідея:** запит на дію оформлюється як окремий об'єкт. Завдяки цьому дію можна зберегти, поставити в чергу, записати в журнал і скасувати.
- **Учасники:** Command, ConcreteCommand, Receiver, Invoker, Client (таблиця вище).
- **Як працює:** Client створює ConcreteCommand і віддає Invoker'у. Invoker викликає `execute()`, а команда звертається до Receiver'а. Invoker не знає, що саме робить команда.
- **Скасування:** команда знає, як відкотити себе (`undo()`); Invoker зберігає виконані команди в стеку й скасовує останню.
- **Чому саме Command у цій ситуації (з опису лаби):** (1) помилкове блокування двигуна треба скасувати → `undo()`; (2) команди, що не дійшли до авто, треба повторити, коли воно на зв'язку → команда — об'єкт, її можна покласти в чергу; (3) служба безпеки вимагає журнал усіх команд → усі команди проходять через один Invoker.
- **Чому не Chain of Responsibility:** тут немає ланцюга обробників, що вирішують «моя це справа чи ні». Запит має відомого виконавця (авто), а нам потрібні черга, журнал і скасування.

### Chain of Responsibility (ланцюг обов'язків) — наш шаблон для Завдання 2
- **Ідея:** запит передається по ланцюгу обробників; кожен або обробляє його (чи зупиняє), або передає наступному. Відправник не знає, хто саме обробить запит.
- **Учасники:** Handler (з посиланням на наступного), ConcreteHandler, Client (таблиця в розділі 3.1).
- **Як працює:** Client збирає ланцюг і віддає запит першій ланці. Ланка виконує свою перевірку: якщо не пройдено — зупиняє ланцюг і повертає причину; якщо пройдено — викликає `next.handle()`. Остання ланка просто завершує ланцюг успішно.
- **Чому саме CoR у цій ситуації (з опису лаби):** (1) перевірки були в одному методі з вкладеними умовами → кожна стала окремим класом; (2) для звичайних і преміальних авто потрібен різний набір перевірок → ланцюг збирається під час виконання; (3) додавання перевірки віку зламало перевірку заборгованості → тепер нова перевірка — це новий клас, існуючі не змінюються (принцип відкритості/закритості); (4) при відмові наступні перевірки не виконуються → ланцюг просто не викликає `next`.
- **Чому не Command:** нам не треба скасовувати, відкладати чи записувати дію. Потрібно послідовно пропустити запит через кілька незалежних перевірок, кожна з яких може його зупинити.
- **Command vs CoR:** Command — «зробити/скасувати/відкласти дію» (запит стає об'єктом); CoR — «хто з кількох обробників візьметься за запит або зупинить його» (запит передається по ланцюгу).

## 5. Можливі питання на захисті
1. Чому тут Command? — потрібні скасування, черга для авто поза зв'язком і журнал (див. вище).
2. Хто в коді Invoker, Receiver, Client? — `RemoteControl`, `Car`, `Main`.
3. Як працює скасування? — команда зберігає стан до виконання; `undoLast()` бере останню команду зі стека й викликає `undo()`.
4. Що буде з командами для авто поза зв'язком? — стають у чергу цього авто і виконуються в `carOnline()`.
5. Як додати нову команду? — новий клас, що реалізує `Command`; `RemoteControl` не змінюється.
6. Чим Command відрізняється від Chain of Responsibility? — див. розділ 4.
7. Чому тут Chain of Responsibility? — перевірки незалежні, мають різний склад і порядок для звичайних/преміальних авто, нова перевірка не повинна чіпати старі (див. розділ 4).
8. Хто в коді Handler, ConcreteHandler, Client? — `AccessCheck`, п'ять `*Check`, `Main` (збирає ланцюги через `TripAccessService`).
9. Як ланцюг передає запит далі? — `AccessCheck.handle()`: якщо `verify()` повернув `null`, викликається `next.handle(request)`; якщо повернув причину — ланцюг зупиняється.
10. Як налаштовується порядок під час виконання? — `TripAccessService.configure(класАвто, перевірки...)` зв'язує ланки через `setNext()` у переданому порядку; для кожного `CarClass` свій ланцюг.
11. Як додати нову перевірку (вік для спорткарів)? — новий клас `AgeCheck extends AccessCheck` з методом `verify()` і додати його в `configure()`; `DebtCheck` та інші не змінюються.
12. Що буде, якщо жодна перевірка не зупинила клієнта? — остання ланка повертає успіх, `TripAccessService` пише «ДОПУСК НАДАНО».
