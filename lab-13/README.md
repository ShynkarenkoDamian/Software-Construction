| Роль у шаблоні | Клас | Що робить |
|---|---|---|
| Command | `Command` | інтерфейс: `execute()`, `undo()`, `getCar()`, `describe()` |
| ConcreteCommand | `OpenDoorsCommand`, `CloseDoorsCommand`, `HazardLightsCommand`, `BlockEngineCommand` | одна віддалена команда; перед виконанням запам'ятовує попередній стан, тому `undo()` його повертає |

| Invoker | `RemoteControl` | приймає команди; авто на зв'язку — виконує, поза зв'язком — кладе в чергу цього авто; веде історію для скасування і журнал |
| Client | `Main` | створює команди й передає їх у `RemoteControl` |
| допоміжний | `Logger` | журнал `[час] [джерело] подія`, час умовний |

### Відповідність вимогам лаби
| Вимога з тексту лаби | Як виконано |
|---|---|
| Кожна команда — окремий об'єкт, що вміє виконатися і скасуватися | 4 класи, реалізують `Command` (`execute`/`undo`) |
| Команди для авто поза зв'язком накопичуються в черзі й виконуються, щойно авто на зв'язку | `RemoteControl.send()` → черга `pending`; `RemoteControl.carOnline()` виконує чергу |
| Останню команду можна скасувати | `RemoteControl.undoLast()` (стек `history`) |
| Усі виконані команди потрапляють у журнал | список `journal`, друк — `printJournal()` |
| Демонстраційний сценарій | `Main.scenarioRemoteCommands()`: «відкрити» + «заблокувати двигун» → скасувати блокування → авто без зв'язку, 2 команди в черзі → авто на зв'язку, команди виконано → журнал |
| У журналі видно, хто отримав запит і хто виконав | `[RemoteControl]` отримав і передав → `[…Command]` виконує → `[Car …]` змінює стан |

## 4. Теорія для захисту

### Command (команда) — наш шаблон
- **Ідея:** запит на дію оформлюється як окремий об'єкт. Завдяки цьому дію можна зберегти, поставити в чергу, записати в журнал і скасувати.
- **Учасники:** Command, ConcreteCommand, Receiver, Invoker, Client (таблиця вище).
- **Як працює:** Client створює ConcreteCommand і віддає Invoker'у. Invoker викликає `execute()`, а команда звертається до Receiver'а. Invoker не знає, що саме робить команда.
- **Скасування:** команда знає, як відкотити себе (`undo()`); Invoker зберігає виконані команди в стеку й скасовує останню.
- **Чому саме Command у цій ситуації (з опису лаби):** (1) помилкове блокування двигуна треба скасувати → `undo()`; (2) команди, що не дійшли до авто, треба повторити, коли воно на зв'язку → команда — об'єкт, її можна покласти в чергу; (3) служба безпеки вимагає журнал усіх команд → усі команди проходять через один Invoker.
- **Чому не Chain of Responsibility:** тут немає ланцюга обробників, що вирішують «моя це справа чи ні». Запит має відомого виконавця (авто), а нам потрібні черга, журнал і скасування.

### Chain of Responsibility (ланцюг обов'язків) — шаблон колеги (Завдання 2)
- **Ідея:** запит передається по ланцюгу обробників; кожен або обробляє його (чи зупиняє), або передає наступному.
- **Учасники:** Handler (з посиланням на наступного), ConcreteHandler, Client.
- **Навіщо в Завданні 2:** перевірки допуску клієнта були в одному методі з вкладеними умовами; з ланцюгом кожна перевірка окрема, склад і порядок налаштовуються під час виконання (звичайні/преміальні авто), нова перевірка не чіпає існуючі.
- **Command vs CoR:** Command — «зробити/скасувати/відкласти дію»; CoR — «хто з кількох обробників візьметься за запит».

## 5. Можливі питання на захисті
1. Чому тут Command? — потрібні скасування, черга для авто поза зв'язком і журнал (див. вище).
2. Хто в коді Invoker, Receiver, Client? — `RemoteControl`, `Car`, `Main`.
3. Як працює скасування? — команда зберігає стан до виконання; `undoLast()` бере останню команду зі стека й викликає `undo()`.
4. Що буде з командами для авто поза зв'язком? — стають у чергу цього авто і виконуються в `carOnline()`.
5. Як додати нову команду? — новий клас, що реалізує `Command`; `RemoteControl` не змінюється.
6. Чим Command відрізняється від Chain of Responsibility? — див. розділ 4.
