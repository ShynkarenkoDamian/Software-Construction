# Лабораторна робота №8 — Пояснення виконання (варіант 8)

**Тема:** Проєктування та рефакторинг взаємодії об'єктів за GRASP
**Предметна область:** логістична компанія, оформлення вантажної відправки
**Мова:** Java 17

Цей документ пояснює, **що** зроблено в кожному завданні, **як** і **чому**.

---

## 0. Що робить програма

Користувач у консолі вводить дані відправника та вантажу. Програма:
1. рахує вартість перевезення (вага × 15 грн, потім коефіцієнт типу доставки: Standard ×1, Express ×1.8, Freight ×1.2);
2. рахує страховку (0.5% від заявленої вартості);
3. створює відправку, ставить статус «відправлено»;
4. зберігає її в реєстр, «надсилає» трекінг-код на email;
5. друкує товарно-транспортну накладну.

Приклад (вага 120 кг, вартість 50 000, Express): перевезення 3240.00, страховка 250.00, разом 3490.00 грн —
це збігається з результатом legacy-коду.

## 1. Структура проєкту

```
src/main/java/logistics/
├── domain/          ← ядро (бізнес-правила), ні від кого не залежить
│   ├── Sender, Cargo, Shipment, ShipmentStatus
│   ├── DeliveryTariff + StandardTariff, ExpressTariff, FreightTariff
│   └── PricingPolicy + DefaultPricingPolicy
├── application/     ← сценарії використання
│   ├── ShipmentController, ShipmentDispatchService, ShipmentFactory
│   ├── CreateShipmentCommand (DTO), TariffRegistry, IdSequence, WaybillFormatter
│   └── ShipmentRepository, TrackingNotifier (інтерфейси)
├── infrastructure/  ← технічні деталі
│   └── InMemoryShipmentRepository, ConsoleEmailNotifier
├── cli/             ← консоль
│   └── ShipmentConsole, ConsoleCommandParser
└── app/Main         ← зшиває все докупи (Composition Root)
```

Залежності йдуть лише в один бік: `cli → application → domain`; `infrastructure → application`.
Домен не знає ні про консоль, ні про сховище.

## Завдання 1. Аудит legacy-коду та Design Rationale

**Що зроблено:** проаналізовано вихідний код, знайдено 10 проблем і записано їх у таблицю
(`docs/adr/ADR-001`). Для кожного рішення створено ADR (5 файлів у `docs/adr/`), а в ADR-002, 003, 004
додано QOC-аналіз (Питання → Варіанти → Критерії → Висновок).

**Головні проблеми legacy:**
* **Anemic Domain Model** — класи `Sender`, `Cargo`, `Shipment` це лише `public`-поля.
* **Bloated метод** — `processShipmentConsole()` робить 9 справ одразу.
* **Спагетті-розгалуження** — `if Express / else if Freight`.
* **Порушення інкапсуляції** — можна записати від'ємну вагу чи довільний статус.
* **Hard-code** — ставки, номер накладної, email зашиті в код.

**Чому ADR + QOC:** лабораторна вимагає не просто змінити код, а обґрунтувати розподіл обов'язків.

## Завдання 2. Information Expert + Creator

### Information Expert (експерт з інформації)
*Правило:* обов'язок отримує той клас, який має потрібні дані.

| Було | Стало | Чому |
|------|-------|------|
| Вартість рахував метод у процесорі | `Cargo.transportFee()`, `insuranceFee()`, `totalCost()` | вага, вартість і тип доставки лежать у `Cargo` |
| Статус — рядок, змінюється будь-де | `Shipment.dispatch()` змінює `ShipmentStatus` | статус належить `Shipment`, він же перевіряє, що відправляти можна лише раз |
| `public` поля | `private final` поля, `record Sender` | захист внутрішнього стану |

### Creator (творець)
*Правило:* об'єкт створює той, хто його містить / тісно з ним працює / має дані для створення.

* `Shipment.create(...)` — статичний фабричний метод, конструктор приватний. Відправка одразу отримує
  розраховану вартість і статус `CREATED`, тому існує лише у валідному стані.
* Конструктори `Cargo` і `Sender` перевіряють дані та кидають `IllegalArgumentException`,
  якщо вони некоректні.
* `ShipmentFactory` збирає `Cargo` + `Sender` + `Shipment` з команди — Creator для всього агрегату.

### Закон Деметри
Замість `shipment.sender.email` — `shipment.senderEmail()`. Об'єкт не «лізе» глибоко в чужу структуру.

## Завдання 3. Controller + Indirection + Pure Fabrication

### Thin Console UI — `ShipmentConsole`
Лише читає рядки з `Scanner`, показує меню й друкує результат. Жодних обчислень.
Розбір чисел із тексту винесено в `ConsoleCommandParser`.

### Controller — `ShipmentController`
Один метод: `registerShipment(CreateShipmentCommand)`. Він просить фабрику створити відправку
та передає її сервісу оформлення. Консолі й розрахунків у ньому немає, залежностей лише 3.

### Чому ще й `ShipmentDispatchService`
Якби контролер сам робив «dispatch → зберегти → email → накладна», у нього було б 6 залежностей
(більше за ліміт 4). Тому ці кроки винесено в окремий application-сервіс.

### Indirection (проміжний шар)
Інтерфейси `ShipmentRepository` та `TrackingNotifier`. Застосунок працює з інтерфейсом,
а `InMemoryShipmentRepository` і `ConsoleEmailNotifier` — це просто змінні реалізації.
Хочемо справжню БД чи SMTP — пишемо новий клас, решта не змінюється.

### Pure Fabrication (штучні класи)
Класів немає в «реальному» світі логістики, але вони потрібні, щоб сутності не перевантажувались:

| Клас | Навіщо |
|------|--------|
| `ShipmentFactory` | збирає агрегат |
| `ShipmentDispatchService` | координує кроки оформлення |
| `WaybillFormatter` | формує текст накладної (не справа `Shipment`) |
| `TariffRegistry` | шукає тариф за назвою |
| `IdSequence` | видає номери (раніше були зашиті в код) |
| `ConsoleCommandParser` | текст → DTO |
| `InMemoryShipmentRepository`, `ConsoleEmailNotifier` | інфраструктура |

## Завдання 4. Polymorphism + Protected Variations

### Було
```java
if ("Express".equalsIgnoreCase(type))      baseTransport *= 1.8;
else if ("Freight".equalsIgnoreCase(type)) baseTransport *= 1.2;
```

### Стало
```java
interface DeliveryTariff { String name(); double applyTo(double baseFee); }
class ExpressTariff implements DeliveryTariff { ... applyTo(x) -> x * 1.8 }
```
`Cargo` просто викликає `tariff.applyTo(...)` і не знає, який саме це тариф.

* **Polymorphism:** поведінка залежить від типу об'єкта, а не від `if`.
* **Dictionary Dispatch:** `TariffRegistry` зберігає `Map<String, DeliveryTariff>`.
* **Protected Variations:** точки, що можуть змінитись, сховані за стабільними інтерфейсами:
  * тип доставки → `DeliveryTariff`;
  * ставки (15 грн/кг, 0.5%) → `PricingPolicy`;
  * сховище → `ShipmentRepository`;
  * сповіщення → `TrackingNotifier`.

**Як додати новий тип «Overnight»:** створити клас `OvernightTariff implements DeliveryTariff`
і додати один рядок `register(new OvernightTariff())` у `TariffRegistry`. Інші класи не змінюються.

## Завдання 5. Метрики (Low Coupling + High Cohesion)

Методика: типи `java.*` не рахуємо; рахуємо класи проєкту. Для LCOM4 виключено конструктори,
статичні фабрики та прості геттери (дозволено методикою).

### 5.1 До рефакторингу (legacy)

| Клас | CBO | LCOM4 | Коментар |
|------|-----|-------|----------|
| `LegacyLogisticsProcessor` | 3 (`Sender`, `Cargo`, `Shipment`) | 1 (формально: один метод) | 9 обов'язків, 31 звернення до чужих полів |
| `Shipment` | 2 (`Sender`, `Cargo`) | — (методів немає) | анемічна сутність |
| `Cargo` | 0 | — | анемічна сутність |
| `Sender` | 0 | — | анемічна сутність |

**Чесне зауваження:** формальні метрики legacy виглядають непогано (CBO = 3, LCOM4 = 1), бо в класі
лише один метод. Реальна проблема видна з інших показників: **31 звернення до чужих полів**
і **9 різних обов'язків в одному методі**. Тому до таблиці додано ці два показники.

### 5.2 Після рефакторингу

| Клас | CBO | Які саме класи | LCOM4 |
|------|-----|----------------|-------|
| `Sender` | 0 | — | 1 |
| `Cargo` | 2 | `DeliveryTariff`, `PricingPolicy` | 1 |
| `Shipment` | 4 | `Sender`, `Cargo`, `PricingPolicy`, `ShipmentStatus` | 1 |
| `ShipmentController` | 3 | `CreateShipmentCommand`, `ShipmentFactory`, `ShipmentDispatchService` | 1 |
| `ShipmentDispatchService` | 4 | `Shipment`, `ShipmentRepository`, `TrackingNotifier`, `WaybillFormatter` | 1 |
| `ShipmentFactory` | 7 | `TariffRegistry`, `PricingPolicy`, `IdSequence`, `CreateShipmentCommand`, `Shipment`, `Sender`, `Cargo` | 1 |
| `TariffRegistry` | 4 | `DeliveryTariff`, `StandardTariff`, `ExpressTariff`, `FreightTariff` | 1 |
| `WaybillFormatter` | 1 | `Shipment` | 1 |
| `ConsoleCommandParser` | 1 | `CreateShipmentCommand` | 1 |
| `ShipmentConsole` | 3 | `ShipmentController`, `ConsoleCommandParser`, `CreateShipmentCommand` | 1 |
| `InMemoryShipmentRepository` | 3 | `ShipmentRepository`, `Shipment`, `WaybillFormatter` | 1 |
| `ConsoleEmailNotifier` | 1 | `TrackingNotifier` | 1 |
| Тарифи (3 шт.), `DefaultPricingPolicy`, `IdSequence` | 0–1 | — | 1 |
| `Main` | багато | — | — (Composition Root) |

### 5.3 Як рахувався LCOM4 (приклад для `Cargo`)
Методи без геттерів: `transportFee`, `insuranceFee`, `totalCost`.
* `transportFee` працює з `weightKg`, `tariff`; `insuranceFee` — з `declaredValue`;
* `totalCost` **викликає** обидва → між ними є ребра графа.
* Усі три методи в одній зв'язній компоненті → **LCOM4 = 1**.

`Shipment`: єдиний небанальний метод `dispatch()` (працює зі `status`) → LCOM4 = 1.

### 5.4 Підсумкове порівняння

| Показник | До | Після |
|----------|----|-------|
| Обов'язків в одному методі/класі | 9 | 1 на клас |
| Звернень до чужих `public`-полів | 31 | 0 (полів `public` немає) |
| CBO сутностей (`Sender`, `Cargo`, `Shipment`) | 0–2, але без логіки | 0, 2, 4 (≤ 4) |
| CBO контролера | — (контролера не було) | 3 (≤ 4) |
| LCOM4 | 1 (формально) | 1 (по кожному класу) |
| Бізнес-логіка в сутностях | немає | є (`Cargo`, `Shipment`) |
| Нова доставка | правка `if-else` | новий клас |

### 5.5 Висновки
1. Ліміт CBO ≤ 4 виконано для сутностей та контролера.
2. `ShipmentFactory` має CBO = 7: вона для того й існує, щоб зібрати агрегат із кількох класів.
   Ліміт з методички стосується сутностей і контролерів. Якщо додати нові залежності, фабрику
   можна розділити на дві.
3. `ShipmentController` має CBO = 3, але якщо вважати ще й тип `Shipment`, який повертає
   `factory.create(...)`, то 4. Ліміт дотримано в обох випадках.
4. Метрики пораховано вручну, а не інструментом.

## Що змінилось відносно legacy (чесно)

* Контактна особа, email, вага, об'єм і заявлена вартість тепер вводяться з консолі
  (у legacy були зашиті: «Іван Петренко», «logistics@company.ua», 120 кг, 1.5 м³, 50 000 грн).
  Номери (770099 для накладної, 55 для відправника) лишились початковими значеннями лічильників.
* Невідомий тип доставки тепер дає помилку (у legacy оброблявся як Standard).
* Об'єм вантажу зберігається й перевіряється, але на ціну не впливає — так само, як і в legacy.
* Додано валідацію (вага > 0, email з `@` тощо).
* Числа в накладній друкуються з двома знаками після коми (`3240.00`).
* Повідомлення `[Реєстр]` та `[Email]` тепер друкуються до тексту накладної (бо накладну друкує CLI
  після повернення з контролера).
