# ADR-004: Тарифи доставки через поліморфізм і захист від змін

## Статус
Прийнято (Accepted)

## Контекст
Вартість залежала від типу доставки через каскад
`if ("Express") ... else if ("Freight") ...`. Додавання нового типу (наприклад, «Overnight»)
вимагало б правити розрахунок. Ставки (15 грн/кг, 0.5%) були вписані у код.

## Questions, Options, Criteria (QOC)

**Question:** Як обробляти різні типи доставки так, щоб нові типи не ламали наявний код?

**Options:**
* A: Залишити `if-else`.
* B: `switch` за `enum`.
* C: Інтерфейс `DeliveryTariff` + окремі класи + пошук у словнику.

**Criteria:**
* Open/Closed: новий тип без зміни старого коду.
* Polymorphism: поведінка визначається типом об'єкта.
* Protected Variations: змінна частина за стабільним інтерфейсом.

**Conclusion:** Option C.

## Рішення
* `DeliveryTariff` (інтерфейс) і три реалізації: `StandardTariff` (×1.0), `ExpressTariff` (×1.8),
  `FreightTariff` (×1.2). **Polymorphism.**
* `TariffRegistry` знаходить тариф за назвою у словнику (Dictionary Dispatch, регістр не важливий).
* `PricingPolicy` (інтерфейс) + `DefaultPricingPolicy` (15 грн/кг, 0.5%) — ставки більше не
  вписані в алгоритм. **Protected Variations.**
* Також за інтерфейсами сховані: сховище (`ShipmentRepository`) та сповіщення (`TrackingNotifier`).

## Наслідки
* **Позитивні:** новий тип доставки = один новий клас + один рядок у `TariffRegistry`;
  зміна ставок не чіпає `Cargo`.
* **Негативні / компроміси:** для трьох простих типів це більше коду, ніж `if-else`; виграш
  з'являється при зростанні кількості типів.
* **Зміна поведінки:** невідомий тип доставки тепер дає помилку (у legacy він мовчки
  трактувався як Standard).
