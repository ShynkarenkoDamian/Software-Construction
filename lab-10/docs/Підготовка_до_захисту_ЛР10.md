## 2. Теорія

### 2.1. Про що ця лабораторна

У лабораторній №9 шаблони вирішували питання «**скільки** об'єктів і **звідки** вони беруться» (один, копія, з пулу). Тут питання інше: «**як** створюється об'єкт і **хто вирішує, якого він класу**». Проблеми з опису ситуацій двох видів:

- спосіб створення **ускладнює розширення**: розгалуження `if/switch` за типом у загальному коді, і кожен новий тип змушує правити цей код;
- спосіб створення **допускає некоректні об'єкти**: об'єкт збирається з несумісних частин або в неповному стані.

### 2.2. Builder (Будівельник)

**Суть.** Відокремлює **покрокове конструювання складного об'єкта** від його подання. Об'єкт збирається окремими, іменованими кроками, а повноцінний результат видається лише на завершальному кроці `build()`.

**Коли застосовувати.**
- Конструктор з великою кількістю параметрів («телескопічний конструктор»): легко переплутати порядок, незрозуміло, що означає кожне значення.
- Частина полів обов'язкова, частина необов'язкова.
- Потрібно **не допустити неповних або некоректних об'єктів**: перевірка виконується в одному місці (у `build()`).
- Є «типові» об'єкти, що збираються однаковою послідовністю кроків.

**Структура:**
- **Builder** — клас (або інтерфейс) з кроками побудови (`withClient(...)`, `withCar(...)`, `withChildSeat()`...) і методом `build()`;
- **Product** — готовий об'єкт; зазвичай **незмінний** (immutable): усі поля `final`, конструктор приватний або пакетний, сеттерів немає;
- **Director** (необов'язково) — клас, що знає **готові послідовності кроків** для типових об'єктів («Поїздка з дитиною», «Аеропорт») і використовує будівельника.

**Fluent-інтерфейс.** Кожен крок повертає `this`, щоб кроки можна було ланцюжити: `builder.client(c).car(a).startTime(t).build()`.

**Валідація в `build()`.** Обов'язкові частини перевіряються на завершальному кроці; при помилці викидається виняток із зрозумілим повідомленням («Неможливо сформувати бронювання: не обрано автомобіль»). Саме це гарантує, що **неповний об'єкт отримати неможливо**.

**Переваги:** читабельне створення, коректність об'єкта гарантована, незмінний результат, повторне використання послідовностей кроків (Director).
**Недоліки:** додатковий клас-будівельник, більше коду, ніж у простого конструктора; для простих об'єктів надлишково.

### 2.3. Factory Method (Фабричний метод)

**Суть.** Визначає **метод створення об'єкта в базовому класі**, а **підкласи вирішують, об'єкт якого класу створити**. Загальний код працює з абстрактним продуктом і не знає конкретних класів.

**Коли застосовувати.**
- Є загальний процес, у якому один крок — створення об'єкта, а конкретний вид об'єкта залежить від контексту (канал, вид оренди, відділення).
- У коді з'явилося розгалуження `if (type == A) new A() else if (type == B) new B()`, яке доводиться правити при кожному новому виді.
- Потрібно, щоб додавання нового виду було **додаванням нових класів**, а не правкою наявного коду (принцип відкритості/закритості, OCP).

**Структура:**
- **Product** — інтерфейс або абстрактний клас продукту;
- **ConcreteProduct** — конкретні продукти;
- **Creator** — абстрактний клас із **фабричним методом** `createProduct()` (абстрактним) і загальною логікою, яка його викликає;
- **ConcreteCreator** — нащадки, що перевизначають `createProduct()` і повертають свій конкретний продукт.

**Зв'язок із Template Method.** Загальний процес у Creator — це зазвичай шаблонний метод (послідовність кроків, часто `final`), де один крок — фабричний метод. Так у Завданні 2: `RentalProcess.rent()` — незмінний процес, `createTrip()` — фабричний метод.

**Переваги:** немає розгалужень за типом, нові види додаються без змін загального коду, слабкий зв'язок із конкретними класами.
**Недоліки:** для кожного нового продукту потрібен новий підклас творця (дві паралельні ієрархії).

### 2.4. Abstract Factory (Абстрактна фабрика)

**Суть.** Надає інтерфейс для створення **сімейств взаємопов'язаних об'єктів** без вказівки їхніх конкретних класів. Кожна конкретна фабрика створює **весь набір продуктів одного сімейства**, тому елементи різних сімейств **змішати неможливо**.

**Коли застосовувати.**
- Є кілька видів продуктів (A, B, C), які **працюють лише разом у межах одного сімейства** (бензинове авто: паливна картка + датчик пального + телематика; електромобіль: зарядна картка + датчик заряду + телематика).
- Помилка виникає, коли кожен елемент вибирається **окремо** (електромобілю видали паливну картку).
- Клієнтський код має працювати з набором через абстракції, не знаючи конкретних класів.

**Структура:**
- **AbstractFactory** — інтерфейс із методом створення кожного виду продукту (`createA()`, `createB()`, `createC()`);
- **ConcreteFactory** — по одній на кожне сімейство; створює продукти саме цього сімейства;
- **AbstractProduct** — інтерфейс для кожного виду продукту (A, B, C);
- **ConcreteProduct** — продукти кожного сімейства;
- **Client** — використовує лише абстрактні фабрику та продукти.

**Узгодженість гарантується структурою:** клієнт отримує всі продукти від **однієї** фабрики, а фабрика фізично створює лише продукти свого сімейства.

**Переваги:** гарантована сумісність продуктів, ізоляція від конкретних класів, нове сімейство додається новими класами (нова фабрика + її продукти) без змін клієнта.
**Недоліки:** додати **новий вид продукту** (четвертий елемент набору) важко: треба змінювати інтерфейс фабрики і всі конкретні фабрики; багато класів (сімейства × види).

### 2.5. Порівняння шаблонів

| Критерій | Builder | Factory Method | Abstract Factory |
|---|---|---|---|
| Головне питання | Як **покроково зібрати** складний об'єкт і не допустити неповного? | Який **клас** об'єкта створити в загальному процесі? | Як створити **узгоджений набір** взаємопов'язаних об'єктів? |
| Що створює | один складний об'єкт | один продукт | сімейство з кількох продуктів |
| Механізм | кроки + `build()` з перевіркою | успадкування: підклас перевизначає метод | композиція: об'єкт-фабрика передається клієнту |
| Типова проблема в умові | конструктор з багатьма параметрами, неповні об'єкти | `if/switch` за типом у загальному процесі | «кожен елемент вибирався окремо», змішані елементи |
| Як додається новий варіант | новий Director/крок | новий підклас творця + продукт | нова фабрика + її продукти |
| Ризик | забули перевірку в `build()`, змінюваний результат | вибух кількості підкласів | складно додати новий вид продукту |

### 2.6. Як визначити шаблон за описом ситуації

| Що написано в умові | Шаблон | Чому |
|---|---|---|
| «конструктор з великою кількістю параметрів», «плутали порядок», «потрапляли об'єкти без …», «обов'язкові і необов'язкові частини», «формується покроково», «типові … однаковою послідовністю кроків» | **Builder** | потрібне покрокове складання з перевіркою на завершальному кроці |
| «процес однаковий, … але конкретний об'єкт залежить від виду/каналу/відділення», «створення через розгалуження за типом», «додавання нового виду вимагало правок у загальному процесі» | **Factory Method** | створення конкретного об'єкта делегується підкласу, розгалуження зникають |
| «набір/комплект з кількох елементів», «різні й працюють лише разом», «кожен елемент вибирався окремо», «змішати неможливо», «код не знає конкретних класів» | **Abstract Factory** | потрібні узгоджені сімейства продуктів |

**Головна пастка: Factory Method чи Abstract Factory?** Обидва «не знають конкретних класів» і дозволяють додавати нове без змін клієнта. Різниця в **кількості продуктів**: Factory Method створює **один** продукт у загальному процесі (одна поїздка); Abstract Factory створює **набір із кількох** взаємозалежних продуктів (три елементи обладнання). Ключова фраза Abstract Factory — «працюють лише разом». Ключова фраза Factory Method — «процес однаковий, об'єкт залежить від виду».

## 3. Завдання 1 — Abstract Factory (виконано)

### 3.1. Умова коротко

Для роботи з авто потрібен узгоджений набір: **модуль телематики, картка поповнення енергії, датчик рівня**. Для бензинових авто, гібридів і електромобілів ці елементи різні й працюють лише разом. У пілоті електромобілю видали паливну картку і підключили датчик рівня пального, бо кожен елемент вибирався окремо.

### 3.2. Чому саме Abstract Factory

Ознаки з тексту:
- «**узгоджений набір** елементів» із **трьох видів** (телематика, картка, датчик);
- «різні й працюють **лише разом**» для кожного типу авто — це сімейства;
- причина помилки — «**кожен елемент вибирався окремо**»;
- вимога «**змішати елементи різних типів неможливо**»;
- «код служби не знає конкретних класів і працює з набором через спільні абстракції»;
- «додавання нового типу (на газу) не потребує змін у коді служби».

Чому не Factory Method: тут не один продукт, а **набір із трьох** взаємозалежних. Чому не Builder: немає покрокового складання одного складного об'єкта, а є вибір цілого сімейства.

### 3.3. Класи і їхні ролі

| Клас | Роль у шаблоні | Призначення |
|---|---|---|
| `VehicleEquipmentFactory` | **Abstract Factory** | Інтерфейс: `createTelematicsModule()`, `createEnergyCard()`, `createLevelSensor()`, `getVehicleType()` |
| `PetrolEquipmentFactory`, `HybridEquipmentFactory`, `ElectricEquipmentFactory` | **Concrete Factory** | Кожна створює набір свого типу авто |
| `GasEquipmentFactory` | Concrete Factory (додано пізніше) | Тип «авто на газу» — окремий пакет `gas` |
| `TelematicsModule`, `EnergyCard`, `LevelSensor` | **Abstract Product** A, B, C | Інтерфейси видів продукту (спільний предок — `EquipmentElement`) |
| `Petrol…`, `Hybrid…`, `Electric…`, `Gas…` (по три) | **Concrete Product** | 12 конкретних елементів, по три на сімейство |
| `FleetMaintenanceService` | **Client** | Служба обслуговування парку: працює лише з абстракціями |
| `ServicedCar` | допоміжний | Авто, введене в роботу з узгодженим набором |
| `EquipmentElement`, `VehicleType` | допоміжні | Спільна абстракція елемента і тип авто (бензинове / гібрид / електромобіль / на газу) |
| `ConsoleLogger` | спільний | Журнал `[час] [джерело] подія` |

### 3.4. Як влаштовано рішення

1. Інтерфейс `VehicleEquipmentFactory` має **три методи створення**, по одному на кожен вид продукту. Це і є «сімейство».
2. Кожна конкретна фабрика (`ElectricEquipmentFactory` та ін.) повертає **лише елементи свого типу**. Фабрика електромобіля фізично не може створити паливну картку.
3. Конкретні продукти мають **пакетну видимість** (клас без `public`): створити їх можна лише в межах пакета, тобто тільки через фабрику свого пакета.
4. `FleetMaintenanceService.commissionCar(plate, factory)`:
   - отримує **одну фабрику** і бере від неї всі три елементи;
   - виводить склад набору, кожен елемент із позначкою типу;
   - робить **перевірку узгодженості**: збирає типи всіх елементів у `EnumSet`; якщо тип один — пише «усі елементи набору належать до типу «…»»;
   - **не містить жодної перевірки типу авто** і не імпортує жодного конкретного класу.
5. Конкретну фабрику обирає код, що викликає службу (`Main`). Це свідомий компроміс: десь хтось має вирішити, яке саме авто вводиться в роботу (у реальній системі — за конфігурацією чи довідником). Головне, що **процес обслуговування** від цього вибору не залежить.

### 3.5. Відповідність вимогам умови

| Вимога з умови | Де реалізовано | Як видно в журналі |
|---|---|---|
| Узгоджений набір елементів одного типу, змішати неможливо | Одна фабрика на набір; фабрика створює лише свої продукти; продукти мають пакетну видимість | Для кожного авто виведено 3 елементи з однаковим «[тип: …]» |
| Код служби не знає конкретних класів, працює через абстракції | `FleetMaintenanceService` оперує лише інтерфейсами | У класі немає імпортів із пакетів `petrol`, `hybrid`, `electric`, `gas` |
| Додавання нового типу не потребує змін у коді служби | Пакет `gas`: `GasEquipmentFactory` + 3 продукти; нове значення `GAS` у `VehicleType` | Запис «Додаємо тип «авто на газу»: лише нові класи… не змінюється» і успішне введення CE4567DD |
| Ввести бензинове, гібрид, електромобіль одним кодом служби | Три виклики `commissionCar` | Три блоки «Введення авто … в роботу» |
| У журналі видно, що всі елементи набору одного типу | `types.size() == 1` у службі | «Перевірка узгодженості: усі елементи набору належать до типу «електромобіль»» |

### 3.7. Обмеження і слабкі місця (бути готовим до питання)

- Додати **новий вид елемента** (скажімо, четвертий — «страховий поліс») — зміни в інтерфейсі `VehicleEquipmentFactory` і в усіх чотирьох фабриках. Це відомий недолік Abstract Factory: легко додавати сімейства, важко додавати види продуктів.
- Вибір конкретної фабрики робить `Main`; у реальній системі це була б конфігурація або реєстр «тип авто → фабрика».
- Перевірка в службі через `EnumSet` — страховка для журналу; реальну гарантію сумісності дає структура (одна фабрика — одне сімейство), а не ця перевірка.
- Нове значення `GAS` додано в `VehicleType` ще на початку; в «чистій» реалізації тип можна було б описувати не enum-ом, а об'єктом, щоб додавати його без змін перелічення.

## 4. Завдання 2 — Factory Method (виконано)

### 4.1. Умова коротко

Процес оренди однаковий: **перевірити авто і клієнта, відкрити поїздку, завершити її, виставити оплату**. Але сама поїздка буває хвилинною, погодинною чи добовою, і кожна має власний розрахунок вартості. Поїздка створювалася через розгалуження за видом оренди, тому додавання оренди на вихідні вимагало правок у загальному процесі.

### 4.2. Чому саме Factory Method

Ознаки з тексту:
- «процес оренди **однаковий**» — є загальний алгоритм;
- конкретний об'єкт (поїздка) **залежить від виду оренди**;
- «створювалася через **розгалуження за видом оренди**»;
- «**додавання нового виду вимагало правок у загальному процесі**»;
- «вид поїздки **визначає відповідний вид оренди**» — тобто підклас «процесу» вирішує, яку поїздку створити;
- «**загальний процес не знає конкретних класів поїздок**».

Чому не Abstract Factory: створюється один продукт (поїздка), а не набір взаємозалежних. Чому не Builder: поїздка не збирається покроково з обов'язкових і необов'язкових частин.

### 4.3. Класи і їхні ролі

| Клас | Роль у шаблоні | Призначення |
|---|---|---|
| `RentalProcess` | **Creator** (абстрактний) | Загальний процес `rent()` (`final`) і абстрактний фабричний метод `createTrip()` |
| `MinuteRental`, `HourlyRental`, `DailyRental` | **Concrete Creator** | Кожен перевизначає `createTrip()` і повертає свій вид поїздки |
| `WeekendRental` | Concrete Creator (додано пізніше) | Оренда на вихідні, окремий пакет `weekend` |
| `Trip` | **Product** (абстрактний) | Поїздка: авто, клієнт, тривалість, вартість; абстрактний `calculateCost()` |
| `MinuteTrip`, `HourlyTrip`, `DailyTrip` | **Concrete Product** | Власні правила розрахунку вартості |
| `WeekendTrip` | Concrete Product (додано пізніше) | Фіксована вартість за вихідні |
| `Car`, `Client` | допоміжні | Спільні класи домену (пакет `domain`) |
| `Main.situation2FactoryMethod()` | Client | Запускає оренду різними творцями |

### 4.4. Як влаштовано рішення

Ядро — клас `RentalProcess`:

```java
public final Trip rent(Car car, Client client, Duration duration) {
    verify(car, client);                       // 1. перевірити авто і клієнта
    Trip trip = createTrip(car, client);       // 2. ФАБРИЧНИЙ МЕТОД — тут і лише тут вибір виду поїздки
    // ... відкрити поїздку
    trip.finish(duration);                     // 3. завершити (вартість рахує сам Trip)
    // ... виставити оплату
    return trip;
}

protected abstract Trip createTrip(Car car, Client client);
```

- Метод `rent()` оголошено **`final`**: підкласи не можуть змінити процес, лише вказують, яку поїздку створити.
- У ньому **немає жодного `if`/`switch` за видом оренди**.
- `HourlyRental.createTrip()` повертає `new HourlyTrip(...)`, `DailyRental` — `DailyTrip` тощо.
- Розрахунок вартості лежить у самій поїздці: `MinuteTrip` — хвилини × ціна за хвилину; `HourlyTrip` — кожна розпочата година; `DailyTrip` — кожна розпочата доба; `WeekendTrip` — фіксована вартість. Тому загальний процес також не знає формул.
- Конкретні поїздки мають пакетну видимість, створюються лише своїм творцем.
- Нова оренда «вихідні» додана **окремим пакетом** `weekend` (два нові класи), а `RentalProcess` і `Trip` не змінювались. Для цього конструктор `Trip` зроблено `protected`, а сам `Trip` — публічним: нащадки в іншому пакеті можуть його розширювати.

### 4.4.1. Приклад розрахунку (поїздка 3 години)

| Вид оренди | Тариф | Вартість |
|---|---|---|
| Хвилинна | 5,00 грн за хвилину | 180 хв × 5,00 = **900,00 грн** |
| Погодинна | 240,00 грн за годину (кожна розпочата) | 3 × 240,00 = **720,00 грн** |
| Добова | 1500,00 грн за добу (кожна розпочата) | 1 доба = **1500,00 грн** |
| На вихідні (додано пізніше) | 1800,00 грн фіксовано | **1800,00 грн** |

### 4.5. Відповідність вимогам умови

| Вимога з умови | Де реалізовано | Як видно в журналі |
|---|---|---|
| Процес оренди описано один раз і не змінюється при додаванні нового виду | `RentalProcess.rent()` (`final`) | Для всіх видів однакова послідовність: перевірка → відкрито → завершено → оплата |
| Вид поїздки визначає відповідний вид оренди, процес не знає конкретних класів | Фабричний метод `createTrip()` у нащадках; `rent()` працює з `Trip` | Різні назви «Хвилинна/Погодинна/Добова оренда» з одного й того ж коду |
| Розгалуження за видом оренди відсутні | У `RentalProcess` немає `if`/`switch` за видом | — (видно в коді) |
| Поїздка 3 години за трьома видами, у журналі різна вартість | `Main.situation2FactoryMethod()` | 900,00 / 720,00 / 1500,00 грн |
| Додати оренду «вихідні» новими класами без зміни процесу | Пакет `weekend` | Запис «Додаємо оренду «вихідні»…» і поїздка на 1800,00 грн |

### 4.6. Що показує демонстрація

```

[09:00:32] [RentalProcess] Поїздку відкрито: Погодинна оренда, авто CE1234AA, клієнт Ткачук
[09:00:33] [RentalProcess] Поїздку завершено, тривалість 3 год 0 хв

### 4.7. Обмеження і слабкі місця

- Паралельні ієрархії: для кожного виду оренди потрібні **два** класи (творець і продукт). Це плата за відсутність розгалужень.
- Вибір творця (`new HourlyRental()`) робить код, що викликає процес, — тобто розгалуження «за видом» просто переноситься на самий верх (у `Main`/конфігурацію), але не потрапляє в процес. У реальній системі це зазвичай вибір за налаштуванням чи вибором клієнта.
- Перевірка авто і клієнта в `verify()` мінімальна (не порожнє посвідчення). Умова не вимагає складнішої логіки.

## 6. Завдання 3 — Builder (виконано)

### 6.0. Умова коротко

Бронювання містить клієнта, авто, час початку, а також необов'язкові опції (дитяче крісло, додаткове страхування, подачу до адреси, коментар). Бронювання створювали конструктором з великою кількістю параметрів, і в систему потрапляли бронювання без авто або з часом початку в минулому. Вимоги: формування покроково; неповне чи некоректне бронювання отримати неможливо (клієнт, авто, час початку не в минулому перевіряються на завершальному кроці з зрозумілим повідомленням); опції можна пропускати, після формування бронювання не змінюється; типові бронювання («Поїздка з дитиною», «Аеропорт») формуються однаковою послідовністю кроків, описаною в одному місці.

### 6.1. Чому саме Builder

Ознаки з тексту умови:
- «створювали **конструктором з великою кількістю параметрів**» — класична проблема телескопічного конструктора;
- «в систему **потрапляли** бронювання **без авто** або з часом початку **в минулому**» — потрібен захист від неповних і некоректних об'єктів;
- «формується **покроково**, кожна частина задається окремою зрозумілою дією»;
- «**обов'язкові** частини перевіряються на **завершальному кроці**», «опції можна **пропускати**» — є обов'язкові й необов'язкові частини;
- «після формування **не змінюється**» — незмінний результат;
- «типові бронювання … **однаковою послідовністю кроків, описаною в одному місці**» — це Director.

Чому не Factory Method: немає загального процесу, у якому змінюється клас продукту. Клас бронювання один, питання не «який клас створити», а «як зібрати коректний об'єкт». Чому не Abstract Factory: немає сімейств взаємозалежних продуктів, збирається один складний об'єкт.

### 6.2. Класи і їхні ролі

| Клас | Роль у шаблоні | Призначення |
|---|---|---|
| `Booking` | **Product** | Незмінне бронювання: клієнт, авто, час початку, опції. Конструктор приватний, поля `final`, сеттерів немає. `describe()` виводить склад читабельно |
| `Booking.Builder` | **Builder** | Вкладений статичний клас. Кроки `withClient`, `withCar`, `withStartTime`, `withChildSeat`, `withExtraInsurance`, `withDeliveryTo`, `withComment` (кожен повертає `this`) і завершальний `build()` з перевіркою |
| `BookingDirector` | **Director** | Знає готові послідовності кроків: `buildChildTrip()` («Поїздка з дитиною») і `buildAirportTrip()` («Аеропорт») |
| `Car`, `Client` | допоміжні | Спільні класи домену (пакет `domain`), використані з Завдання 2 |
| `ConsoleLogger` | спільний | Журнал `[час] [джерело] подія` |
| `Main.situation3Builder()` | Client | Відтворює демонстраційний сценарій |

### 6.3. Де виконується валідація і як гарантується незмінність

**Валідація** — єдине місце, `Booking.Builder.build()`. Перевірки йдуть у такому порядку, перша ж невдала зупиняє формування:
1. клієнт заданий — інакше «Неможливо сформувати бронювання: не вказано клієнта»;
2. авто задано — інакше «…: не обрано автомобіль»;
3. час початку заданий — інакше «…: не вказано час початку»;
4. час початку не раніше за «зараз» — інакше «…: час початку в минулому».

У разі помилки будівельник пише повідомлення в журнал і кидає `IllegalStateException` з тим самим текстом, тому **об'єкт `Booking` у такому разі не створюється взагалі**. Перевірка «не в минулому» використовує `Clock`, який передається в конструктор будівельника: у демонстрації годинник фіксований (08.11.2026 09:00), тому журнал відтворюваний; час «рівно зараз» дозволено.

**Незмінність і неможливість обійти будівельника:**
- усі поля `Booking` — `final`, сеттерів немає (`Client`, `Car`, `String`, `LocalDateTime` теж незмінні);
- конструктор `Booking(Builder)` **приватний**: зовні (з `Main` чи будь-якого іншого класу) `new Booking(...)` не скомпілюється. Будівельник є вкладеним класом, тому має доступ до приватного конструктора і до свого стану, а більше ніхто;
- бронювання копіює значення з будівельника в момент `build()`: подальші виклики `withXxx()` на тому самому будівельнику вже створений об'єкт не змінюють (перевірено одноразовим тестом поза репозиторієм);
- кроки можна викликати в будь-якому порядку, а обов'язкові частини гарантовано перевіряються лише в `build()`: це і є «завершальний крок» з умови.

### 6.4. Відповідність вимогам умови

| Вимога з умови | Де реалізовано | Як видно в журналі |
|---|---|---|
| Бронювання формується покроково, кожна частина окремою дією | Кроки `withXxx()` (fluent-інтерфейс) | Записи «Крок: клієнт — …», «Крок: авто — …», «Крок: дитяче крісло» |
| Неповне чи некоректне бронювання отримати неможливо | `build()` перевіряє клієнта, авто, час початку; конструктор `Booking` приватний | «Неможливо сформувати бронювання: не обрано автомобіль» і «…: час початку в минулому» |

### 6.6. Обмеження реалізації (бути готовим до питання)

- Будівельник перевіряє наявність обов'язкових частин і час початку, але не перевіряє, чи вільне авто і чи дійсне посвідчення клієнта: умова цього не вимагає, а доступність авто — тема іншої роботи.
- `build()` зупиняється на **першій** помилці. Альтернатива — зібрати всі помилки й повідомити одразу; для умови достатньо одного зрозумілого повідомлення.
- Помилка виражена непередбачуваним (unchecked) `IllegalStateException`: виклик, що забув обробити його, зупинить програму; у `Main` для цього є `attemptBooking`.
- Один будівельник призначений для одного бронювання, не потокобезпечний; `BookingDirector` створює новий будівельник на кожен виклик, тому типові бронювання не впливають одне на одне.
- Повторний виклик кроку перезаписує попереднє значення (останній виграє). Це не заборонено умовою.
- Адреса аеропорту й тексти коментарів у Director — умовні константи.
- Час у демонстрації фіксований через `Clock.fixed`, тому приклад не залежить від справжнього часу на комп'ютері.

## 9. Питання, які можуть поставити, та відповіді

**Чим Abstract Factory відрізняється від Factory Method?**
Factory Method створює один продукт, і вибір класу робить підклас творця (успадкування). Abstract Factory створює набір взаємопов'язаних продуктів, і гарантує їхню узгодженість; клієнт отримує об'єкт-фабрику (композиція). Нерідко методи Abstract Factory самі реалізовані як фабричні методи.

**Як у Завданні 1 гарантовано, що елементи не змішаються?**
Клієнт отримує всі три елементи від однієї фабрики, а кожна фабрика створює лише свої продукти. Конкретні продукти мають пакетну видимість, тому створити їх у обхід фабрики не можна. Перевірка типів у службі лише дублює гарантію для журналу.

**Де в Завданні 1 розгалуження за типом авто?**
Немає ні в службі, ні у фабриках. Вибір фабрики відбувається в `Main` (місце, де відомий тип авто); у реальній системі це конфігурація чи реєстр.

**Що робити, якщо потрібен ще один вид елемента (наприклад, страховий поліс)?**
Додати метод у `VehicleEquipmentFactory`, новий абстрактний продукт і реалізувати його у всіх конкретних фабриках. Це відомий недолік Abstract Factory.

**Чому `rent()` оголошено `final`?**
Щоб процес оренди не можна було змінити в нащадках: вони лише вказують, яку поїздку створити. Це шаблонний метод, у якому один крок — фабричний метод.

**Чим фабричний метод краще за розгалуження `switch` за видом оренди?**
Розгалуження змушує правити загальний процес при кожному новому виді. З фабричним методом новий вид — це нові класи (`WeekendRental`, `WeekendTrip`), а загальний код не змінюється (принцип відкритості/закритості).

**Чому розрахунок вартості лежить у `Trip`, а не в `RentalProcess`?**
Бо формула залежить від виду оренди. Якби вона була в процесі, там знову з'явилося б розгалуження за видом.

**Чому `Trip` публічний, а конкретні поїздки — пакетні?**
`Trip` — абстракція, з якою працює процес, і яку розширює `WeekendTrip` з іншого пакета. Конкретні поїздки створюються лише своїми творцями, тому видимість мінімальна.

**У чому тоді проблема з Factory Method — «розгалуження просто переїхало»?**
Вибір творця (який вид оренди) залишається в коді вищого рівня, але він зник із **процесу**, який найбільше страждав від правок. Для вибору можна використати реєстр чи конфігурацію.

**Чим Builder відрізняється від Abstract Factory і Factory Method?**
Builder збирає **один складний об'єкт покроково** і перевіряє його повноту; він не про вибір класу і не про сімейства. Factory Method вирішує, який клас створити в загальному процесі, Abstract Factory видає узгоджений набір кількох продуктів. Див. п. 2.5.

**Для чого Director у Builder?**
Для типових послідовностей кроків («Аеропорт», «Поїздка з дитиною»): послідовність описана в одному місці й використовується повторно. Director не обов'язковий: без нього будівельник працює, як у повному бронюванні в `Main`. Він залежить лише від будівельника, не від продукту.

**Чому результат Builder має бути незмінним?**
Умова вимагає, щоб бронювання після формування не змінювалось. Поля `final` і відсутність сеттерів гарантують, що перевірений у `build()` об'єкт лишається коректним: ніхто не зможе потім прибрати авто чи виставити час у минулому.

**Чому Builder — вкладений клас, а не окремий?**
Щоб конструктор `Booking` був справді приватним. Вкладений клас має доступ до приватних членів, а ззовні `new Booking(...)` не скомпілюється. З окремим класом конструктор довелося б робити пакетним, і будь-який клас пакета міг би його викликати в обхід перевірки.

**Чому перевірка в `build()`, а не в кожному кроці?**
Кроки можна викликати в будь-якому порядку, і на момент кроку інших частин ще немає. Вимога умови: обов'язкові частини перевіряються саме на завершальному кроці. Це також одне місце для правил валідації.

**Чому виняток, а не `null`?**
`null` легко проігнорувати, і некоректний стан піде далі. Виняток із текстом причини змушує обробити помилку, а некоректний об'єкт не існує взагалі. У демонстрації його перехоплює `attemptBooking`.

**Чим Builder кращий за конструктор з багатьма параметрами або сеттери (JavaBeans)?**
Конструктор: легко переплутати порядок однотипних параметрів, незрозуміло, що значить кожен (`null`, `true`, `false`), немає перевірки повноти. Сеттери: між створенням і заповненням об'єкт існує в неповному, змінюваному стані. Builder дає іменовані кроки, перевірку в одному місці й незмінний результат.

**Навіщо `Clock` у будівельнику?**
Для перевірки «час початку не в минулому» потрібен поточний час. Якщо брати його напряму (`LocalDateTime.now()`), демонстрація не буде відтворюваною. Фіксований `Clock` робить журнал однаковим при кожному запуску й дає змогу перевірити саме межу «у минулому».

**Чи можна використати один будівельник для кількох бронювань?**
Технічно так (результат уже створеного бронювання не змінюється), але стан будівельника зберігається між викликами, тому легко перенести зайву опцію. Тому Director створює новий будівельник на кожне бронювання.

**Які порушення принципів SOLID вирішують ці шаблони?**
Factory Method і Abstract Factory — принцип відкритості/закритості (OCP) і інверсію залежностей (DIP): процес залежить від абстракцій, а не від конкретних класів. Builder — читабельність і цілісність об'єкта.

## 10. Чесні примітки: що в проєкті є умовним

Домен у документі «Домени варіантів» описує сутності, але не конкретні значення. Нижче те, що довелося задати для демонстрації, а не взято з умови. Викладачеві варто сказати про це прямо, якщо запитає.

| Що | Значення | Примітка |
|---|---|---|
| Номери авто | CE1234AA (з умови), CE2345BB, CE3456CC, CE4567DD | перший з умови, решта — умовні |
| Типи і склад наборів | «паливна картка (бензин)», «комбінована картка», «картка зарядної мережі», «газова картка» та ін. | описи виведені з умови (паливна картка, датчик рівня пального, електромобіль) і логіки типів; умовні тексти |
| Клієнт у Завданні 2 | Ткачук, посвідчення «ВХС 123456» | прізвище збігається з ЛР9; номер посвідчення умовний |
| Ціни видів оренди | 5,00 грн/хв; 240,00 грн/год; 1500,00 грн/добу; 1800,00 грн за вихідні | умовні; умова наголошує лише, що розрахунки різні |
| Правила округлення | кожна розпочата година / доба | умовне рішення |
| Оренда «вихідні» | фіксована вартість незалежно від тривалості | умовне рішення, змодельовано поїздку 3 години за умовою |
| Перевірка авто і клієнта | авто і посвідчення водія клієнта не порожні | мінімальна перевірка |
| «Поточний» час у Завданні 3 | 08.11.2026 09:00 (фіксований `Clock`) | потрібен для перевірки «не в минулому» і відтворюваного журналу |
| Дати бронювань | 09.11.2026 10:00 (повне), 10.11.2026 05:30 («Аеропорт»), 09.11.2026 15:00 («Поїздка з дитиною»), 09.11.2026 12:00 (без авто), 07.11.2026 12:00 (минуле) | умовні |
| Адреса подачі | «вул. Головна, 12» | умовна (така ж адреса клієнта в ЛР9) |
| Склад типових бронювань | «Аеропорт» = подача до «Міжнародний аеропорт «Чернівці»» + коментар; «Поїздка з дитиною» = дитяче крісло + додаткове страхування + коментар | умова називає типові бронювання, але не визначає їхній склад |
| Додаткова демонстрація | бронювання з часом початку в минулому | умовою не вимагається, показує другу обов'язкову перевірку |
| Порядок перевірок у `build()` | клієнт → авто → час початку → «не в минулому» | перша невдала зупиняє формування |
| Тип помилки | `IllegalStateException` | умова вимагає лише зрозуміле повідомлення |
| Час у журналі | відлік від 09:00:00 | дозволено умовою |

Рішення, що виходять за текст умови: пакетна видимість конкретних продуктів/поїздок; `final` для `rent()`; вкладений клас `Booking.Builder` із приватним конструктором продукту; додаткова перевірка узгодженості типів у `FleetMaintenanceService`; розміщення нових класів (газ, вихідні) у окремих пакетах, щоб наочно показати, що наявний код не змінювався.

Перевірка збірки: код (усі три завдання) скомпільовано без попереджень (`javac -Xlint:all`, JDK 21) і запущено, вивід збережено в `docs/sample_output.txt`. `pom.xml` складено стандартно (Java 17, UTF-8), але саме `mvn` у середовищі підготовки не запускався, тому перший запуск через Maven варто перевірити локально. Для коректного виведення кирилиці в консолі `Main` примусово встановлює UTF-8; якщо в консолі Windows усе одно виводяться «ієрогліфи», запускайте з IntelliJ або виконайте `chcp 65001`.
